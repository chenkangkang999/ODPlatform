# ADR-003：运行配置三层与优先级，配置里不写机器相关值

| 项目 | 内容 |
|---|---|
| 状态 | ✅ Accepted |
| 决策日期 | 2026-10-24 |

## 背景

同一份代码要在不同机器上跑：开发机（有 GPU）、CI（Linux、无 GPU）、产线机（可能只有 CPU）。
配置既要能表达"这次怎么跑"，又不能把某台机器的特征固化进仓库。

现状（本决策确认并加固）：

- 运行配置在 `configs/runtime/*.yaml`（进 git），字段由 pydantic 定义并带默认值；
- 命令行参数可临时覆盖；
- `configs/runtime/infer_pipeline.yaml` 管帧源与美化。

曾出现过一次反面案例：为了"避免 torch 退回 CPU 时静默用 CPU 跑"，把 `device` 写成了 `0`。
这确实能尽早报错，但**把"本机只有一张 0 号卡"固化进了仓库**，换机器就失效 ——
属于典型的机器相关硬编码，已撤销。

## 备选方案

- 方案 A：只留 YAML，不接受 CLI 覆盖 —— 简单，但每次试参数都要改文件（且会污染 git 状态）
- 方案 B：只留 CLI，不要 YAML —— 命令行会变得很长，且无法沉淀"这次实验的配方"
- 方案 C：YAML 为底 + CLI 覆盖 + 内置默认值兜底（本决策）

## 决定

方案 C，并加两条约束：

1. **优先级固定为 CLI > YAML > DEFAULT**，且必须可观测：`odp-infer`/`odp-train` 启动时
   逐字段打印取值与来源（`config_log.py`），审计快照里记录覆盖链。
2. **配置里不写机器相关值**：

   | 字段 | 写法 | 理由 |
   |---|---|---|
   | `device` | 保持 `null`（自动：有 CUDA 用 GPU，否则 CPU） | 写死卡号换机器即失效；要临时固定用 `--device 0` |
   | `model` | 给名字或相对引用（`yolov8n.pt`），由 `refs.resolve_*` 解析 | 避免绝对路径 |
   | 路径类 | 相对仓库根（见 ADR-002） | 可移植 |
   | `batch`/`imgsz` | 写"通常合适"的值，机器差异用 CLI 覆盖 | 8G 显存与 24G 显存需求不同 |

3. 若确实需要"本机专属"的固定值，用**环境变量或 CLI**，不要改仓库里的 yaml。

## 理由

1. 仓库里的配置是**团队的默认共识**，不是某台机器的快照。
2. 三层结构让"默认 → 本次调整 → 一次性覆盖"各得其所，试参数不必弄脏 git。
3. 可观测性（打印来源）解决了"我明明改了配置怎么没生效"这类排查成本最高的问题。

## 后果

- 正面：同一份仓库可在开发机（GPU）、CI（CPU）上跑出各自正确的结果；
  配置生效路径一目了然。
- 负面：`device: null` 时，torch 是 `+cpu` 构建的话会**静默用 CPU**。
  缓解手段是运行开头打印的"运行环境概览"（`CUDA可用/GPU数量/显存`）——
  它是每次运行的固定输出，把"静默"变成"可见"；README 也把 CUDA 版 torch 的安装单列一节。
- 中性：字段变多后 pydantic 模型成为单一事实源，改字段要同时更新配置模板（`odp-gen-config`）。

## 撤销条件

- 需要按环境分层（dev/prod 两套默认值）时，引入 profile 机制并由新 ADR 取代；
- 若未来支持"机器档案"（把本机能力写进 `.odp-meta/` 而非仓库配置），
  则本 ADR 需要补充那一层。
